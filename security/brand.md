# Band 设计、原理与跨平台实践

> 一份关于加密存储容器的完整技术文档

---

## 一、简介

### 1.1 什么是 Band 容器

**Band 容器**是一种面向移动端（Android / iOS）设计的**加密存储方案**。其核心思想是将一个逻辑上的加密卷，物理上切分为多个固定大小的独立单元——称为 **Band**（波段）。每个 Band 独立加密、独立存储，通过一个轻量级的 **Manifest**（清单）文件维护完整的文件索引。

如果把传统加密卷比作一个**整体保险箱**——存取任何文件都需要搬运整个保险箱——那么 Band 容器就是一个**智能抽屉仓库**：每个抽屉独立上锁，账本告诉你文件在哪个抽屉，修改时只换一个抽屉，而不用搬动整个仓库。

### 1.2 设计目标

| 目标               | 说明                                                 |
| ------------------ | ---------------------------------------------------- |
| **高性能随机访问** | 读取任意文件只需定位并解密对应的 Band，而非整个卷    |
| **低写放大**       | 小文件修改只重写一个 Band（如 8MB），而非整个卷      |
| **崩溃一致性**     | Copy-on-Write 机制保证任意时刻断电不损坏数据         |
| **跨平台兼容**     | 容器本质是普通文件夹，iOS/Windows/macOS 均可直接识别 |
| **完整性保护**     | 每 Band 独立 GCM Tag，篡改即报错                     |
| **秒级换密**       | Keybag 独立于数据，更换密码只需重加密 Keybag         |

### 1.3 与 macOS sparsebundle 的对比

Band 容器的设计灵感部分来源于 macOS 的 **sparsebundle** 格式——后者同样将磁盘映像切分为 8MB 的 band 文件，被 macOS 的 FileVault 和 Time Machine 广泛使用。但 Band 容器在以下几个方面做出了针对性改进：

| 维度      | macOS sparsebundle       | Band 容器                  |
| --------- | ------------------------ | -------------------------- |
| 加密算法  | AES-XTS（仅机密性）      | AES-GCM（机密性 + 完整性） |
| 换密码    | 需重加密整个卷           | 秒级（仅重加密 Keybag）    |
| 跨平台    | macOS 专属（需内核挂载） | 普通文件夹，全平台可用     |
| 拷贝安全  | 挂载中拷贝易损坏         | COW 保证一致性             |
| Band 大小 | 固定 8MB                 | 可配置（1MB~8MB）          |

## 二、应用场景

### 2.1 个人隐私保险箱

用户将敏感文档、照片、视频存入加密容器，只有输入正确密码后才能访问。适合存储身份证扫描件、银行对账单、私密照片等。

### 2.2 跨平台加密同步

由于 Band 容器本质是普通文件夹，用户可以将其放在 iCloud、Google Drive、Dropbox 等云盘中同步。云端存储的是加密数据，服务商无法窥探内容，而用户在所有设备上均可通过 App 解密访问。

### 2.3 企业移动办公

员工在手机上处理企业敏感文档时，所有数据以 Band 容器形式加密存储。即使用户手机丢失，他人也无法读取容器内容。配合 DocumentsProvider（Android）或 File Provider（iOS）扩展，可向系统文件管理器暴露只读的加密文件视图。

### 2.4 媒体库加密存储

视频、音乐等大文件以 Band 容器存储，播放时按需解密，不影响流媒体播放体验。Band 大小可针对媒体库调优（如 8MB），减少索引数量，提升顺序读取性能。

### 2.5 安全备份

将 Band 容器目录整体备份到外部存储或云端，由于 COW 机制保证一致性，备份过程中即使中断也不会产生损坏的半成品数据。

## 四、包文件产物 Tree

一个 Band 容器在磁盘上表现为一个**普通文件夹**，内部包含以下文件：

```
MyVault/                          ← 容器根目录
│
├── .manifest                     ← 清单文件（明文/轻量编码）
│   └── 记录：文件目录树、每个文件的 band_id + offset + size
│
├── .keybag                       ← 密钥串文件（密文，用户密码加密）
│   └── 记录：每个 Band 的 AES-256-GCM 密钥（加密存储）
│
├── band_0001.band                ← 第 1 个数据波段（8MB 加密数据 + IV + Tag）
├── band_0002.band                ← 第 2 个数据波段
├── band_0003.band                ← 第 3 个数据波段
├── ...
│
└── .trash/                       ← （可选）待 GC 回收的旧 Band
    ├── band_0001_old.band
    └── band_0005_old.band
```

**文件说明**：

| 文件         | 格式            | 是否加密  | 说明                                   |
| ------------ | --------------- | --------- | -------------------------------------- |
| `.manifest`  | JSON / Protobuf | ❌ 明文    | 文件索引，公开目录结构但无数据内容     |
| `.keybag`    | 二进制密文      | ✅ AES-GCM | 所有 Band 密钥，用用户密码派生密钥加密 |
| `.band` 文件 | 自定义二进制    | ✅ AES-GCM | 实际数据，每 Band 独立 IV 和 GCM Tag   |
| `.trash/`    | 目录            | ✅         | 待删除的旧 Band（COW 产生）            |

## 五、文件内存布局图

### 5.1 单个 `.band` 文件的物理布局

每个 Band 文件在磁盘上的精确字节结构如下（假设 Band 大小为 8MB = 8,388,608 字节）：

```
+-------------------+---------------------------------------------------+-------------------+
|   字节偏移量       |                  数据区域                          |     长度/说明       |
+-------------------+---------------------------------------------------+-------------------+
| 0 ~ 15            |  **IV (Initialization Vector)**                    |  16 字节           |
|                   |  每次写入时随机生成的 16 字节随机数                |                    |
+-------------------+---------------------------------------------------+-------------------+
| 16 ~ (16+8,388,607)|  **Ciphertext (密文区)**                           |  8,388,608 字节    |
|                   |  实际文件数据经 AES-256-GCM 加密后的结果           |                    |
|                   |  (明文按需填充至 Band 大小对齐)                    |                    |
+-------------------+---------------------------------------------------+-------------------+
| 8,388,624 ~       |  **GCM 认证标签 (Authentication Tag)**             |  16 字节           |
| 8,388,639         |  用于校验密文完整性，防篡改                        |                    |
+-------------------+---------------------------------------------------+-------------------+

物理总大小 = 16 (IV) + 8,388,608 (数据) + 16 (Tag) = 8,388,640 字节
```

### 5.2 Manifest 中的逻辑偏移 vs 物理偏移

**关键规则**：Manifest 中记录的 `offset` 和 `size` 指向**加密前的明文数据**位置，而非物理文件偏移。

```json
// Manifest 记录示例
{
  "files": {
    "report.pdf": {
      "band_id": 1,
      "offset": 0,        // ← 明文数据的起始位置
      "size": 1048576     // ← 明文数据大小（1MB）
    }
  }
}
```

**物理读取位置换算**：

```
物理文件读取起始 = Manifest.offset + 16 (跳过 IV 头)
物理文件读取长度 = Manifest.size
```

## 七、实现原理

### 7.1 加密机制

**算法**：AES-256-GCM（认证加密 AEAD）

- **AES-256**：对称加密，密钥长度 256 位
- **GCM 模式**：Galois/Counter Mode，同时提供机密性和完整性保护

**每 Band 独立密钥**：
- 每个 Band 使用独立的 AES-256 密钥
- 所有密钥存储在 Keybag 中，用主密码加密
- 每个 Band 每次写入使用全新的随机 IV

**AES-GCM 的关键限制**：
- 单个密钥 + 同一 Nonce 组合下，最大加密数据量为 **64 GB**
- 每 Band 独立密钥的设计天然规避了这一限制——每个 Band 最多 8MB，远低于 64GB 上限
- Nonce（IV）必须唯一，否则 GCM 安全性崩溃

### 7.2 密钥派生与验证

```
用户密码 + Salt → PBKDF2/Argon2 → 主密钥 (KEK)
                                          ↓
                              解密 Keybag 获取所有 Band 密钥
                                          ↓
                              验证：尝试解密 Keybag 的校验字段
                                          ↓
                              成功 → 容器解锁 | 失败 → 密码错误
```

### 7.3 换密码（秒级）

由于 Band 密钥存储在 Keybag 中，而非直接由用户密码派生：

1. 用户输入新密码
2. 用新密码派生新 KEK
3. 用新 KEK 重新加密 Keybag 中的所有 Band 密钥
4. 原子写入新 Keybag

**整个过程只涉及 Keybag 文件（几 KB），与数据量无关，秒级完成。**

### 7.4 Copy-on-Write（COW）写入

修改文件时，**绝不原地覆盖**：

1. 读取原 Band 到内存，解密
2. 在内存中修改数据
3. 用新 IV 重新加密整个 Band
4. 写入**新的** Band 文件（`band_XXXX_new.band`）
5. **原子更新** Manifest，指向新 Band
6. 异步删除旧 Band

**崩溃一致性保证**：
- 若在步骤 5 之前崩溃：旧数据完好，新 Band 是垃圾（下次 GC 清理）
- 若在步骤 5 之后崩溃：Manifest 已指向新数据，修改生效

## 九、设计模式

| 设计模式       | 应用场景           | 说明                                                                 |
| -------------- | ------------------ | -------------------------------------------------------------------- |
| **门面模式**   | `BandContainer` 类 | 为复杂的子系统（Manifest、Keybag、BandPool、加密）提供统一简洁的接口 |
| **策略模式**   | 加密算法           | 可替换加密实现（AES-GCM / AES-XTS / ChaCha20-Poly1305）              |
| **工厂模式**   | Band 创建          | `BandFactory` 负责创建新的 Band 文件，分配 ID 和密钥                 |
| **单例模式**   | 容器实例           | 每个容器路径对应一个 `BandContainer` 实例                            |
| **观察者模式** | 后台 GC            | 空闲空间低于阈值时，触发 Compaction 观察者执行碎片整理               |
| **对象池模式** | Band 文件句柄      | `BandPool` 维护 LRU 文件句柄池，避免频繁打开/关闭                    |
| **命令模式**   | 写操作             | 每次写入封装为 Command，支持 COW 和回滚                              |
| **代理模式**   | 文件访问           | `FileProxy` 拦截读写请求，透明处理加解密                             |

## 十一、关键算法解释

### 11.1 文件 → Band 映射算法

```
输入: 文件路径 path, 文件大小 size
输出: List<(band_id, offset, size)>

算法:
1. 从 Manifest 查找 path
2. 若不存在 → 返回 null
3. 获取该文件的 block 列表
4. 每个 block 包含 (band_id, offset, size)
5. 按顺序返回所有 block
```

### 11.2 偏移量物理转换

```
输入: band_id, logical_offset (明文坐标), read_length
输出: physical_offset, physical_length

physical_offset = 16 (IV头) + logical_offset
physical_length = read_length + 16 (GCM Tag)

// 注意：需按 16 字节对齐
aligned_offset = (physical_offset / 16) * 16
extra_bytes = physical_offset - aligned_offset
final_read_length = physical_length + extra_bytes
```

### 11.3 空闲空间分配（首次适应）

```
输入: 需要分配的 size
输出: (band_id, offset) 或 null

算法:
1. 遍历 Manifest.free_blocks
2. 找到第一个 size >= 所需大小的空闲块
3. 分配该块的前 size 字节
4. 更新 free_blocks（剩余部分继续保留）
5. 若无足够空闲 → 创建新 Band
```

### 11.4 碎片整理（Compaction / GC）

```
触发条件: 活跃数据 / 物理占用 < 阈值 (如 60%)

算法:
1. 暂停新写入（< 1秒）
2. 遍历 Manifest 所有存活文件
3. 按顺序读取每个文件的密文数据
4. 重新打包写入新的 Band 文件（顺序写入）
5. 生成新 Manifest
6. 🔒 原子切换 Manifest
7. 删除所有旧 Band 文件
8. 恢复写入
```

## 十三、常见问题与解决方案

### Q1: 修改 1KB 文件为什么要重写整个 8MB Band？

**原因**：AES-GCM 是整体认证加密模式，无法单独重加密部分数据而不破坏完整性验证。

**解决方案**：
- 文档库使用 **1MB Band**（写放大从 8000 倍降至 1024 倍）
- 后台异步 GC 回收旧 Band

### Q2: 频繁修改小文件会导致大量垃圾 Band 怎么办？

**原因**：COW 每次修改产生新 Band，旧 Band 变为垃圾。

**解决方案**：
- 后台 **Compaction** 定期整理（充电/空闲时触发）
- 合并存活文件到新 Band，删除垃圾 Band
- 阈值触发机制（活跃/物理 < 60%）

### Q3: 视频播放跨 Band 会卡顿吗？

**原因**：如果每次跨 Band 都打开/关闭文件，会产生 IO 延迟。

**解决方案**：
- **BandPool** 维护文件句柄池，跨 Band 读取无文件打开开销
- **异步预读** + **双缓冲**流水线
- 数学换算定位 Band，O(1) 复杂度

### Q4: 换密码为什么要秒级完成？

**原理**：Band 密钥存储在 Keybag 中，换密码只需用新 KEK 重新加密 Keybag（几 KB），与数据量无关。

**实现**：新旧密码验证 → 派生新 KEK → 重加密 Keybag → 原子写入

### Q5: 容器在拷贝/同步中损坏怎么办？

**原因**：传统单文件加密卷在拷贝中若中断，整个文件损坏。

**解决方案**：COW + Manifest 原子更新保证**任何时候**拷贝都是一致状态。即使拷贝中中断，源容器完好，目标端只是部分文件。

### Q6: AES-GCM 的 64GB 限制会影响 Band 容器吗？

**原因**：AES-GCM 单密钥单 Nonce 组合下最大加密 64GB。

**解决方案**：每 Band 独立密钥，单 Band 最大 8MB，远低于 64GB 上限，天然规避限制。

### Q7: 如何防止暴力破解密码？

**解决方案**：
- PBKDF2/Argon2 慢哈希（100,000+ 迭代）
- 增加登录失败延迟
- 可选硬件级密钥保护（Android Keystore / iOS KeyChain）

## 十四、最佳实践建议

### 14.1 Band 大小选择

| 使用场景       | 推荐 Band 大小 | 理由                                   |
| -------------- | -------------- | -------------------------------------- |
| 视频/照片库    | **8 MB**       | 大文件多，减少索引条目，顺序读性能最优 |
| 文档/代码库    | **1 MB**       | 小文件多，降低修改写放大               |
| 混合使用       | **4 MB**       | 折中方案                               |
| 高频小文件修改 | **512 KB**     | 极致降低写放大（但索引增多）           |

### 14.2 安全实践

1. **密码强度**：至少 12 字符，包含大小写字母 + 数字 + 特殊字符
2. **迭代次数**：根据设备性能设为 100,000~1,000,000
3. **内存清理**：解锁后立即擦除原始密码，密钥用完即焚
4. **自动锁定**：App 进入后台 5 分钟后自动锁定容器
5. **硬件支持**：Android 使用 Keystore，iOS 使用 KeyChain 保护主密钥

### 14.3 性能优化

1. **文件句柄池**：维护 LRU 缓存，避免频繁 open/close
2. **预读取**：视频播放时异步预读后续 Band
3. **缓存策略**：热数据明文缓存（LRU，32MB）
4. **硬件加速**：使用 Android 的 Crypto API / iOS 的 CryptoKit 进行硬件 AES 加速
5. **异步 GC**：在充电、空闲时执行 Compaction，不阻塞用户操作

### 14.4 跨平台注意事项

| 平台        | 文件系统限制         | 建议                                          |
| ----------- | -------------------- | --------------------------------------------- |
| **Android** | 无特殊限制           | 使用 `RandomAccessFile` 或 `FileChannel`      |
| **iOS**     | 沙盒限制             | 使用 `FileManager`，注意 Background Task 限制 |
| **Windows** | 路径长度 260 字符    | Band 命名保持简短（如 `b_%04x.band`）         |
| **macOS**   | 大小写不敏感（默认） | 文件路径统一小写或使用大小写敏感分区          |

### 14.5 备份与恢复

1. **备份整个容器文件夹**即可（包含 `.manifest`、`.keybag` 和所有 `.band`）
2. **增量备份**：只备份新增/修改的 Band 文件（通过文件修改时间判断）
3. **跨设备恢复**：复制容器文件夹到新设备，使用同一密码解锁
4. **云端同步**：容器可放在 iCloud/Google Drive 中，云端只存密文

## 十五、总结

Band 容器通过**化整为零**的设计哲学，在移动端实现了一个兼具**高性能**、**强安全**、**跨平台**的加密存储方案。

**核心优势**：
- ✅ 随机访问效率媲美裸盘
- ✅ 小文件修改写放大可控（通过可调 Band 大小）
- ✅ 崩溃一致性（COW + 原子 Manifest）
- ✅ 秒级换密码
- ✅ 完整性保护（AES-GCM）
- ✅ 跨平台兼容（普通文件夹）

**代价**：
- ⚠️ 需要 App 自身实现文件系统逻辑（无法像 sparsebundle 那样由内核挂载）
- ⚠️ 系统原生应用无法直接访问（但这也是隐私保护的优势）

Band 容器是一个经过深思熟虑的设计，它在**安全性**、**性能**和**可用性**之间找到了一个精准的平衡点，尤其适合在移动端构建隐私优先的加密存储应用。
