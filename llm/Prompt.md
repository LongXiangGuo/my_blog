# 提示词工程全景白皮书：从认知到架构的系统化指南

## 引言

提示词不再仅仅是“问问题的语句”，而是**高维语义空间中的向量寻址指令**。其本质是通过文本排列组合，操纵千亿参数神经网络的激活模式。提示词工程的演进，本质是从**“写一句指令”**向**“构建AI认知编排系统”**的跃迁。

---

## 第一部分：认知基石——提示词的深层本质

### 1. 由浅入深的认知三阶

| 层级                   | 认知定位     | 核心关注点                                                                                                    |
| :--------------------- | :----------- | :------------------------------------------------------------------------------------------------------------ |
| **浅层（语法）**       | 指令编写     | 角色扮演、少样本示例（Few-shot）、清晰分隔符、四要素（指令/上下文/输入/输出）。                               |
| **中层（修辞与逻辑）** | 引导推理路径 | 思维链（CoT）、思维树（ToT）、ReAct（推理+行动）、正反双向约束。                                              |
| **深层（元逻辑）**     | 操纵模型机制 | 注意力机制（Attention）寻址（近因/首因效应）、降低答案“熵”值、系统提示词（System Prompt）对KV Cache的预填充。 |

## 第二部分：三维工程视角——产研运一体化的“铁三角”

成功的提示词工程必须跳出纯文本视角，融入产品、开发与架构的生存逻辑。

| 维度                       | 核心矛盾与策略                                                                                                     | 关键落地动作                                                                                                         |
| :------------------------- | :----------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------- |
| **产品视角（体验）**       | **矛盾**：用户不懂AI语法，却要求高质量输出。<br>**策略**：隐式提示词（按钮触发后台拼接）、防呆机制、品牌调性收敛。 | 将复杂的System Prompt藏在“专业/通俗/小红书风”按钮背后；建立安全护栏Guardrails防止越狱。                              |
| **开发视角（成本与契约）** | **矛盾**：Prompt是上线后需频繁调优的非确定性“代码”。<br>**策略**：契约化、可观测、高密度压缩。                     | 强制**JSON Schema**输出；建立Prompt版本管理（CI/CD）与A/B测试；埋点记录Token消耗与延迟。                             |
| **架构视角（系统调度）**   | **矛盾**：大模型是黑盒，系统却要求确定性。<br>**策略**：解耦、路由、分布式认知。                                   | **语义路由**（意图分类分发）；**多智能体协作**（主管+垂直专家）；**语义缓存**（Embedding相似度复用结果，降本增效）。 |

## 第三部分：实现方案体系——让提示词“可编程”

将提示词从“炼金术”升级为“系统工程”。

### 1. 结构化与动态生成
- **多层提示架构**：元提示层（角色/安全）+ 任务提示层（分析/生成）+ 动态注入层（实时RAG知识）。
- **上下文感知生成**：根据情绪分析、历史记录动态调整Prompt内容。
- **滑动窗口管理**：提取关键摘要注入，防止上下文过长导致“上下文坍塌”。

### 2. 智能路由与缓存
- **语义路由（Semantic Router）**：轻量级分类器判定意图，分发至专用子Prompt，避免“大而全”的高昂成本。
- **语义缓存（Semantic Caching）**：将用户Query转为Embedding，命中相似历史请求则直接返回，**延迟可降低至毫秒级（降低100倍）**。

### 3. 生命周期管理（PEaC）
- **Prompt Registry（注册表）**：将提示词视为代码资产，纳入Git版本控制。
- **自动化优化闭环**：抓取线上Badcase（如用户点击“重新生成”）→ 转化为负面样本 → 自动触发下一轮Prompt迭代。

## 第四部分：全网模板与框架分类大全

根据全网各渠道（含B站博主、GitHub开源库、CSDN技术社区、OpenAI/Google官方等）的系统性整理，目前共收录到**24个主流提示词框架**。这些框架按复杂度分为**5大类**：

| 类别       | 特点                                | 数量 | 包含框架                                  |
| :--------- | :---------------------------------- | :--- | :---------------------------------------- |
| **基础类** | 极简结构，3个核心元素，5-10分钟掌握 | 6个  | RTF、TAG、ERA、APE、BAB、CTF              |
| **流程类** | 元素3-4个，包含因果链条和步骤规划   | 6个  | ICIO、RISE、RACE、CARE、SPAR、SAGE        |
| **规范类** | 约束严格、专业性强，减少幻觉问题    | 6个  | TREF、GRADE、ROSES、COAST、TRACE、CO-STAR |
| **探索类** | 支持迭代优化和多方案探索            | 4个  | CRISPE、RASCEF、BROKE、PATFU              |
| **综合类** | 最复杂，适合超大规模综合任务        | 3个  | CREATE、RTCROS、PECRA                     |

---

### 🟢 一、基础类（极简快速）—— 日常快速任务

> **特点**：极简结构，仅含3个核心元素，是所有高级模式的基础。5-10分钟即可掌握，解决80%日常对话痛点。

| 框架    | 要素流程                                               | 核心问题                           | 适用领域         | 典型场景                            |
| :------ | :----------------------------------------------------- | :--------------------------------- | :--------------- | :---------------------------------- |
| **RTF** | `角色(Role)` → `任务(Task)` → `格式(Format)`           | 谁来做？做什么？怎么做？           | 通用日常         | 写邮件、生成文案、整理信息          |
| **TAG** | `任务(Task)` → `行动(Action)` → `目标(Goal)`           | 做什么？怎么做？为何做？           | 任务执行         | 明确要做什么、怎么执行、达成什么    |
| **ERA** | `期望(Expectation)` → `角色(Role)` → `行动(Action)`    | 想要什么结果？谁来做？怎么做？     | 结果导向         | 需要明确输出标准或验收条件的任务    |
| **APE** | `行动(Action)` → `目的(Purpose)` → `期望(Expectation)` | 做什么？为什么？要什么？           | 快速入门         | 短平快场景，快速获取答案            |
| **BAB** | `背景(Background)` → `行动(Action)` → `结果(Benefit)`  | 背景是什么？做什么？带来什么好处？ | 说服/提案        | 写提案、推荐方案、说服他人          |
| **CTF** | `上下文(Context)` → `任务(Task)` → `格式(Format)`      | 背景信息是什么？做什么？什么格式？ | 需背景信息的任务 | RTF的变体，当任务需要背景信息时使用 |

**选择建议**：当你面对日常简单任务、需要在5分钟内获得可用答案时，从这6个框架中任选其一即可。**RTF**是最通用的起点，**APE**适合“短平快”场景。

---

### 🟡 二、流程类（中等复杂、分步执行）—— 中等复杂度任务

> **特点**：在基础类上的延伸，元素数量适中（3-4个），存在因果链条或相互影响关系。开始引入更专业的概念（如输入输出、步骤规划）。

| 框架     | 要素流程                                                                | 核心问题                                   | 适用领域   | 典型场景                         |
| :------- | :---------------------------------------------------------------------- | :----------------------------------------- | :--------- | :------------------------------- |
| **ICIO** | `指令(Instruction)` → `背景(Context)` → `输入(Input)` → `输出(Output)`  | 做什么？什么背景？用什么数据？输出什么？   | 结构化任务 | 软件开发文档、数据分析、代码审查 |
| **RISE** | `角色(Role)` → `输入(Input)` → `步骤(Steps)` → `期望(Expectation)`      | 谁来做？处理什么？分几步？要什么结果？     | 需分步执行 | 多步骤任务分解、流程化工作       |
| **RACE** | `角色(Role)` → `行动(Action)` → `背景(Context)` → `期望(Expectation)`   | 谁来做？做什么？什么背景？要什么结果？     | 角色驱动   | 专业咨询、顾问类任务             |
| **CARE** | `背景(Context)` → `行动(Action)` → `结果(Result)` → `示例(Example)`     | 什么背景？做什么？要什么结果？参考什么？   | 内容优化   | 内容创作与迭代、训练计划设计     |
| **SPAR** | `场景(Scene)` → `问题(Problem)` → `行动(Action)` → `结果(Result)`       | 什么场景？什么问题？怎么做？什么结果？     | 复盘优化   | 发布后复盘、问题根因分析         |
| **SAGE** | `情境(Situation)` → `行动(Action)` → `目标(Goal)` → `期望(Expectation)` | 什么情境？做什么？目标是什么？要什么结果？ | 战略规划   | 项目规划、方案设计               |

**选择建议**：当任务需要处理结构化数据、涉及明确输入输出、或需要多步骤分解时，选择流程类框架。**ICIO**是最通用的选择，尤其适合数据分析和技术任务。

---

### 🟠 三、规范类（专业领域、精准输出）—— 特定专业领域

> **特点**：包含**强制性的约束条件和质量要求**，确保输出质量可控，减少“幻觉”问题。专业性强，确保输出符合行业标准。

| 框架        | 要素流程                                                                                                   | 核心问题                                           | 适用领域      | 典型场景                     |
| :---------- | :--------------------------------------------------------------------------------------------------------- | :------------------------------------------------- | :------------ | :--------------------------- |
| **TREF**    | `任务(Task)` → `要求(Requirements)` → `期望(Expectations)` → `格式(Format)`                                | 做什么？必须满足什么标准？达到什么质量？什么格式？ | 专业写作      | 法律文书、技术文档、合同起草 |
| **GRADE**   | `目标(Goal)` → `角色(Role)` → `受众(Audience)` → `细节(Details)` → `期望(Expectation)`                     | 目标是什么？谁来做？给谁看？具体细节？期望效果？   | 精准沟通      | 面向特定受众的专业内容       |
| **ROSES**   | `角色(Role)` → `目标(Objective)` → `场景(Scenario)` → `期望(Expectation)` → `步骤(Steps)`                  | 谁来做？目标？场景？期望？分几步？                 | 小型活动/选题 | 活动策划、选题规划           |
| **COAST**   | `上下文(Context)` → `目标(Objective)` → `行动(Action)` → `场景(Scenario)` → `任务(Task)`                   | 背景？目标？做什么？场景？具体任务？               | 复杂场景      | 跨部门协作、项目启动         |
| **TRACE**   | `任务(Task)` → `角色(Role)` → `受众(Audience)` → `上下文(Context)` → `期望(Expectation)`                   | 做什么？谁来做？给谁看？背景？期望？               | 沟通优化      | 邮件、报告、演示文稿         |
| **CO-STAR** | `上下文(Context)` → `目标(Objective)` → `风格(Style)` → `语气(Tone)` → `受众(Audience)` → `响应(Response)` | 背景？目标？什么风格？什么语气？给谁看？输出什么？ | 内容创作      | 品牌营销文案、发布会内容     |

> **重要说明**：`Requirements`（要求）和`Format`（格式）的区别在于——**Requirements是强制性的**（违反即不合格），而**Format是建议性的**（偏好或推荐）。

**选择建议**：当任务属于法律、技术文档、合同等**需要严格遵循规范**的领域，且对输出准确性和合规性要求极高时，选择规范类框架。

---

### 🔴 四、探索类（深度探索与迭代）—— 迭代优化与多方案探索

> **特点**：支持多次迭代、多方案对比、持续优化。融合了OKR等成熟管理方法论。

| 框架       | 要素流程                                                                                                                 | 核心问题                                             | 适用领域          | 典型场景                         |
| :--------- | :----------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------- | :---------------- | :------------------------------- |
| **CRISPE** | `能力/角色(Capacity/Role)` → `背景洞察(Insight)` → `具体任务(Statement)` → `风格/个性(Personality)` → `尝试(Experiment)` | 什么能力？什么背景？具体做什么？什么风格？如何迭代？ | 创意定制          | 广告TVC、品牌创意、作文批改      |
| **RASCEF** | `角色(Role)` → `行动(Action)` → `步骤(Script)` → `背景(Content)` → `示例(Example)` → `格式(Format)`                      | 谁来做？做什么？分几步？背景？参考什么？什么格式？   | 系统化任务        | 校园活动策划、简历优化、旅游攻略 |
| **BROKE**  | `背景(Background)` → `角色(Role)` → `目标(Objectives)` → `关键结果(Key Results)` → `演变(Evolve)`                        | 什么背景？谁来做？目标？关键指标？如何迭代？         | 商业分析/深度规划 | 品牌策略、系统规划、用户增长     |
| **PATFU**  | `问题(Problem)` → `行动(Action)` → `思考(Thought)` → `反馈(Feedback)` → `更新(Update)`                                   | 什么问题？怎么做？如何思考？反馈如何？怎么更新？     | 迭代优化          | 持续改进的任务、敏捷开发         |

**选择建议**：当任务高度模糊、需要多方案探索、或需要持续迭代优化时，选择探索类框架。**BROKE**融合了OKR方法论，适合商业分析和战略规划。**CRISPE**适合需要创意和风格定制的任务。

---

### 🟣 五、综合类 —— 最复杂的综合任务

> **特点**：包含最多元素，适合超大规模、跨部门、端到端的综合任务。

| 框架       | 要素流程                         | 适用领域   | 典型场景           |
| :--------- | :------------------------------- | :--------- | :----------------- |
| **CREATE** | 综合多要素（具体要素因版本而异） | 超复杂任务 | 大型项目、系统设计 |
| **RTCROS** | 综合多要素                       | 全流程管理 | 端到端产品开发     |
| **PECRA**  | 综合多要素                       | 战略级任务 | 企业级AI应用       |

**选择建议**：仅当任务复杂度极高、涉及多个部门/系统/阶段时，才考虑综合类框架。绝大多数日常任务用前四类即可。

---

### 🔵 六、技术方法分类（10大家族）

除了上述按**复杂度**分类的框架外，提示词技术还可从**底层方法**角度归纳为10大技术家族。这些家族可以**叠加组合**使用——生产环境中的提示词往往同时使用多个家族。若从底层技术视角看，所有模板均归属于以下技术家族，实际生产中，必须组合多个家族（如：设定+结构+智能体+验证）才能保证生产级质量。

| 家族                    | 核心方法                       | 代表技术                  | 适用领域             |
| :---------------------- | :----------------------------- | :------------------------ | :------------------- |
| **设定(Framing)**       | 角色指派、人格设定、受众定义   | “你是一位资深Java工程师…” | 所有场景的基础       |
| **结构(Structure)**     | XML标签、Markdown分段、分隔符  | `<instruction>`标签       | 长提示词、复杂任务   |
| **示例(Demonstration)** | 零样本、单样本、多样本、类比式 | Few-shot learning         | 格式敏感任务         |
| **推理(Reasoning)**     | 思维链、自我一致性、思维树     | Chain-of-Thought (CoT)    | 数学、逻辑、复杂推理 |
| **分解(Decomposition)** | 提示链、任务拆分、分步执行     | 先规划后执行              | 大型项目、多步骤任务 |
| **检索(Retrieval)**     | RAG、知识库、向量检索          | 检索增强生成              | 需要外部知识的任务   |
| **智能体(Agent)**       | ReAct、工具调用、多智能体协作  | 思考-行动-观察循环        | 自动化工作流         |
| **验证(Verification)**  | 自验证、事实核查、一致性检查   | “请检查你的回答”          | 高准确性要求         |
| **约束(Constraint)**    | 护栏、格式强制、负面约束       | JSON Schema强制           | 生产环境             |
| **元处理(Meta)**        | 元提示、提示词自优化           | “帮我优化这个提示词”      | 提示词工程本身       |

> **实战要点**：一个生产级提示词通常组合多个家族。例如，三步分类器通常需要 **设定 + 结构 + 约束**；研究型智能体往往需要 **设定 + 智能体 + 检索 + 验证**。

## 第五部分：如何选择？——决策总览图

当你面对一个新任务时，可按以下决策流程选择框架和配套技术。

### 一、复杂度优先决策树

```text
你的任务是什么？
        │
        ▼
任务简单明确？ ──────────────────────────→ 【基础类】（RTF/TAG/APE）
        │
        ▼ 复杂
需要分步骤执行或跨部门协作？ ──────────→ 【流程类】（ICIO/RISE/CO-STAR）
        │
        ▼ 特殊行业/专业
你是营销/金融/HR/开发？ ──────────────→ 【规范类】（GRADE/TREF/CO-STAR）
        │
        ▼ 高度模糊/需创意
战略规划/头脑风暴/系统重构？ ────────→ 【探索类】（BROKE/CRISPE）
        │
        ▼ 超大规模综合
跨部门端到端/企业级系统？ ────────────→ 【综合类】（CREATE等）
```

### 二、详细决策步骤

**第一步：任务复杂度评估**

| 任务复杂度 | 推荐框架类别 | 具体推荐       | 预计学习成本 |
| :--------- | :----------- | :------------- | :----------- |
| ★☆☆☆☆      | 基础类       | RTF            | 5分钟        |
| ★★☆☆☆      | 基础类       | APE / TAG      | 5-10分钟     |
| ★★★☆☆      | 流程类       | ICIO / RISE    | 15分钟       |
| ★★★★☆      | 规范类       | TREF / CO-STAR | 20分钟       |
| ★★★★★      | 探索类       | BROKE / CRISPE | 30分钟       |
| ★★★★★+     | 综合类       | CREATE         | 1小时+       |

**第二步：任务类型判断**
- 有标准答案（分类、提取、代码）→ 零样本 / 少样本
- 开放式生成（写作、头脑风暴）→ 思维链 + 示例

**第三步：外部知识需求**
- 需要最新/专有知识（公司文档）→ + RAG（检索增强生成）
- 不需要外部知识（通用知识）→ 纯提示词

**第四步：是否需要执行操作**
- 需要调用工具/API/数据库 → + Agent（智能体）
- 纯信息生成 → 标准提示词

**第五步：安全敏感场景？**
- 涉及用户隐私/支付/合规 → **强制叠加全链路安全防护**（见第七部分）

**第六步：能否接受延迟/成本？**
- 高频高频/性价比优先 → **开启语义缓存 + 小模型路由**

## 第六部分：高频场景实战模板（以“流程指令”呈现）

不同业务场景下，Prompt需固化为标准的“填空式”工作流。

### 场景一：移动端/软件开发（UI还原与Bug修复）
- **工作流**：`角色（高级iOS/Android工程师）` → `背景（机型/系统版本）` → `目标（像素级还原/帧率稳定60fps）` → `计划（分析布局树→提取Theme变量→处理生命周期）` → `任务（生成代码/修复Crash）`。
- **黄金法则**：必须加上“**考虑生命周期**”、“**避免内存泄漏**”、“**适配全面屏/安全区域**”等触发词。

### 场景二：智能客服（高频高并发）
- **工作流**：`意图识别路由（分类器）` → `RAG检索企业知识库` → `情绪感知动态注入（消极则安抚）` → `结构化输出（JSON含置信度与人工介入标识）`。
- **架构重点**：高频问题走语义缓存，极低成本响应。

### 场景三：代码生成（高准确率）
- **工作流**：`三层提示设计（架构设计→接口定义→具体实现）` → `Few-shot风格示例` → `自检指令（审查语法/逻辑漏洞）`。
- **约束**：复杂分布式事务场景需人工干预，模板类CRUD代码可全自动。

### 场景四：数据分析与报表
- **工作流**：`明确JSON/Markdown Schema` → `强制展示计算过程（CoT防幻觉）` → `数据不足时引导反问`。
- **红线**：“**不要编造缺失数据**”。

---

## 第七部分：安全纵深防御体系（不可缺失的基石）

大模型无法区分“系统指令”与“用户恶意数据”，因此安全必须贯穿全链路。

| 防御层级                          | 核心方案                                                                             | 目的                                          |
| :-------------------------------- | :----------------------------------------------------------------------------------- | :-------------------------------------------- |
| **输入层（Pre-inference）**       | Prompt Shield检测、PII脱敏、越狱模式识别、格式验证。                                 | 在到达模型前拦截恶意载荷。                    |
| **指令-数据分离（In-inference）** | 结构化分隔符（`###系统` vs `###用户`）、Real User Instruction（RUI）中间件强制隔离。 | 防止用户输入覆盖System Prompt（提示词注入）。 |
| **模型内部（Intra-inference）**   | 激活引导（Activation Steering）、DefensiveToken插入、DRIP表示编辑。                  | 将对抗性Token从指令流形中推开。               |
| **输出层（Post-inference）**      | 敏感信息过滤、违规内容审核、自适应响应精炼。                                         | 防止模型输出幻觉或机密数据。                  |
| **可观测性**                      | 安全事件审计日志、红队对抗测试、实时告警。                                           | 持续验证防御有效性。                          |

> **企业落地铁律**：**高风险场景（SQL查询、代码执行）** 必须加强校验；**低风险场景（闲聊）** 适当放宽，以平衡用户体验。

---

## 总结

提示词工程的演进，本质是从**“写一句指令”**向**“构建AI认知编排系统”**的跃迁。

- **对新人**：从 `RTF` 或 `ICIO` 框架入手，掌握基础语法与CoT。
- **对产品经理**：学会将用户需求翻译成“隐式提示词”，确保品牌调性一致。
- **对开发者**：将提示词当作API契约，强约束JSON格式，建立版本管理与Badcase闭环。
- **对架构师**：放弃“万能长Prompt”，拥抱“意图路由 + 多专家矩阵 + 语义缓存”的分布式调度架构。
