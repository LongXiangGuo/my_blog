# iOS 多线程锁完全指南：从基础到实战

> 一文吃透 iOS 开发中的 10 种锁机制，理解原理、掌握选型、避坑指南。从**分类**、**工作原理**、**底层实现**、**性能对比**到**实战场景**，辅以代码示例，力求全面而实用。

---

## 一、锁的核心概念

锁的核心思想非常简单：**线程在访问共享资源前必须先获取锁，访问结束后释放锁**。但围绕这个简单思想，衍生出了多种不同特性的锁。

### 1.1 按等待机制分类

| 类型                    | 等待方式                                | 适用场景                 |
| :---------------------- | :-------------------------------------- | :----------------------- |
| **自旋锁 (Spin Lock)**  | 线程“忙等”，持续占用 CPU 轮询检查锁状态 | 临界区极短，锁竞争不激烈 |
| **互斥锁 (Mutex Lock)** | 线程进入“睡眠”，让出 CPU，等待唤醒      | 临界区可能耗时较长       |

自旋锁避免了线程上下文切换的开销，但会浪费 CPU 时间；互斥锁节省 CPU 资源，但有休眠/唤醒的开销。

### 1.2 按功能特性分类

| 类型           | 核心特性                            |
| :------------- | :---------------------------------- |
| **普通互斥锁** | 同一时刻只允许一个线程访问          |
| **递归锁**     | 允许同一个线程多次加锁，防止死锁    |
| **条件锁**     | 结合互斥锁和条件变量，支持等待/通知 |
| **读写锁**     | 多读并行、写独占                    |
| **信号量**     | 控制并发访问的线程数量              |

## 二、iOS 各类锁详解

### 2.1 `OSSpinLock`（自旋锁 · 已废弃）

> ⚠️ **重要提示**：iOS 10.0 起已废弃，新代码禁止使用。

**工作原理**：等待锁的线程进入无限循环（忙等），不断检查锁状态，直到获取到锁。底层通过原子操作（如 `__sync_lock_test_and_set`）实现。

**致命缺陷——优先级反转**：
- 低优先级线程持有锁，高优先级线程忙于等待（自旋）
- 低优先级线程得不到调度，无法释放锁
- 高优先级线程永远等不到锁

**替代方案**：`os_unfair_lock`

---

### 2.2 `os_unfair_lock`（低级别互斥锁）

`OSSpinLock` 的安全替代品，iOS 10.0+ 可用。

**特点**：
- 等待线程**休眠**而非忙等
- **非公平锁**：等待线程不保证按顺序获得锁
- 极轻量，性能优秀

**使用示例**：
```objc
#import <os/lock.h>

@interface CacheManager : NSObject {
    os_unfair_lock _cacheLock;
    NSMutableDictionary *_cache;
}
@end

@implementation CacheManager

- (instancetype)init {
    self = [super init];
    if (self) {
        _cacheLock = OS_UNFAIR_LOCK_INIT;
        _cache = [NSMutableDictionary dictionary];
    }
    return self;
}

- (void)setObject:(id)obj forKey:(NSString *)key {
    os_unfair_lock_lock(&_cacheLock);
    if (obj) {
        _cache[key] = obj;
    } else {
        [_cache removeObjectForKey:key];
    }
    os_unfair_lock_unlock(&_cacheLock);
}

- (id)objectForKey:(NSString *)key {
    os_unfair_lock_lock(&_cacheLock);
    id obj = _cache[key];
    os_unfair_lock_unlock(&_cacheLock);
    return obj;
}

@end
```

**适用场景**：高性能缓存、计数器、基础数据结构的保护。

### 2.3 `pthread_mutex`（POSIX 互斥锁）

跨平台的 C 语言级别锁，是 iOS 中许多高级锁的底层基础。

**特点**：
- 通过 `pthread_mutexattr_settype` 可配置为**普通锁**或**递归锁**
- 性能优秀，直接调用系统函数
- 需手动管理生命周期（`init` / `destroy`）

**类型**：
```c
pthread_mutexattr_t attr;
pthread_mutexattr_init(&attr);
pthread_mutexattr_settype(&attr, PTHREAD_MUTEX_NORMAL);   // 普通锁
pthread_mutexattr_settype(&attr, PTHREAD_MUTEX_RECURSIVE); // 递归锁
pthread_mutex_init(&mutex, &attr);
```

---

### 2.4 `NSLock`（Foundation 互斥锁）

对 `pthread_mutex` 的面向对象封装，API 更友好。

**特点**：
- **非递归锁**：同一线程重复加锁会导致死锁
- 提供了 `tryLock` 和 `lockBeforeDate:` 等便捷方法

**使用示例**：
```objc
NSLock *lock = [[NSLock alloc] init];

- (void)threadSafeMethod {
    [lock lock];
    // 临界区代码
    [lock unlock];
}
```

---

### 2.5 `@synchronized`（互斥锁 · 最便捷）

使用最简洁的锁，传入任意 OC 对象作为锁标识。

**特点**：
- **递归锁**：底层实现是递归互斥锁
- 性能开销大，不适合性能敏感场景
- 编译后转换为 `objc_sync_enter` / `objc_sync_exit`

**使用示例**：
```objc
// 单例模式
+ (instancetype)sharedInstance {
    static id instance = nil;
    @synchronized (self) {
        if (!instance) {
            instance = [[self alloc] init];
        }
    }
    return instance;
}
// 现代推荐使用 dispatch_once，性能更好
```

**底层原理**：
```objc
// 这段代码
@synchronized(obj) {
    // do something
}
// 编译后等价于
@objc_sync_enter(obj);
// do something
@objc_sync_exit(obj);
```

`objc_sync_enter` 底层维护一个全局哈希表，以对象地址为 key，存储递归锁信息。

### 2.6 `NSRecursiveLock`（递归锁）

允许**同一个线程**多次获取锁而不死锁。

**工作原理**：
- 内部维护 `_owner`（持有线程）和 `_count`（加锁计数）
- 同一线程再次加锁 → 仅 `_count++`，线程不挂起
- 解锁时 `_count--`，归零时锁真正释放

**使用示例**：
```objc
NSRecursiveLock *recursiveLock = [[NSRecursiveLock alloc] init];

- (void)traverseNode:(TreeNode *)node {
    [recursiveLock lock];
    // 处理当前节点
    NSLog(@"Node: %@", node.value);
    
    for (TreeNode *child in node.children) {
        [self traverseNode:child]; // 递归调用，递归锁防止死锁
    }
    [recursiveLock unlock];
}
```

**⚠️ 注意**：性能开销高于普通互斥锁，仅在确实需要递归加锁时使用。

### 2.7 `NSCondition`（条件锁）

封装了 `pthread_mutex` 和 `pthread_cond`（条件变量），支持线程间基于条件的等待/通知。

**核心方法**：
| 方法             | 作用                             |
| :--------------- | :------------------------------- |
| `wait`           | 释放锁并挂起当前线程，等待被唤醒 |
| `waitUntilDate:` | 带超时的等待                     |
| `signal`         | 唤醒一个等待线程                 |
| `broadcast`      | 唤醒所有等待线程                 |

**使用示例（生产者-消费者）**：
```objc
NSCondition *condition = [[NSCondition alloc] init];
BOOL hasData = NO;
NSMutableArray *buffer = [NSMutableArray array];

// 生产者
- (void)produce {
    [condition lock];
    [buffer addObject:@"data"];
    hasData = YES;
    [condition signal];  // 唤醒等待的消费者
    [condition unlock];
}

// 消费者
- (void)consume {
    [condition lock];
    while (!hasData) {
        [condition wait];  // 释放锁并等待
    }
    id data = [buffer firstObject];
    [buffer removeObjectAtIndex:0];
    hasData = (buffer.count > 0);
    [condition unlock];
}
```

**为什么要用 `while` 而非 `if`？**
- 防止**虚假唤醒（Spurious Wakeup）**
- 被唤醒后再次检查条件是否真正满足

---

### 2.8 `NSConditionLock`（条件锁 · 进阶版）

`NSCondition` 的变种，通过 **整数值条件** 控制线程执行顺序。

**核心方法**：
```objc
- (void)lockWhenCondition:(NSInteger)condition;   // 条件满足时加锁
- (void)unlockWithCondition:(NSInteger)condition;  // 解锁并设置新条件
```

**使用示例（任务按顺序执行）**：
```objc
NSConditionLock *orderLock = [[NSConditionLock alloc] initWithCondition:0];

// 任务 1（必须 condition == 0）
- (void)task1 {
    [orderLock lockWhenCondition:0];
    NSLog(@"执行任务 1");
    [orderLock unlockWithCondition:1];
}

// 任务 2（必须 condition == 1）
- (void)task2 {
    [orderLock lockWhenCondition:1];
    NSLog(@"执行任务 2");
    [orderLock unlockWithCondition:2];
}

// 任务 3（必须 condition == 2）
- (void)task3 {
    [orderLock lockWhenCondition:2];
    NSLog(@"执行任务 3");
    [orderLock unlockWithCondition:0];
}
```

### 2.9 `dispatch_semaphore`（信号量）

GCD 提供的信号量机制，功能强大且性能优秀。

**核心方法**：
| 方法                                    | 作用                             |
| :-------------------------------------- | :------------------------------- |
| `dispatch_semaphore_create(long value)` | 创建信号量，value 为初始资源数   |
| `dispatch_semaphore_wait`               | 信号量 > 0 时减 1 继续，否则阻塞 |
| `dispatch_semaphore_signal`             | 信号量加 1，唤醒等待线程         |

**用途 1：实现互斥锁（初始值 = 1）**：
```objc
dispatch_semaphore_t semaphore = dispatch_semaphore_create(1);

- (void)threadSafeMethod {
    dispatch_semaphore_wait(semaphore, DISPATCH_TIME_FOREVER);
    // 临界区
    dispatch_semaphore_signal(semaphore);
}
```

**用途 2：控制并发数量（初始值 = N）**：
```objc
// 最大并发 3 个上传任务
dispatch_semaphore_t uploadSemaphore = dispatch_semaphore_create(3);

- (void)uploadFiles:(NSArray<NSData *> *)files {
    for (NSData *data in files) {
        dispatch_async(dispatch_get_global_queue(0, 0), ^{
            dispatch_semaphore_wait(uploadSemaphore, DISPATCH_TIME_FOREVER);
            [self doUpload:data completion:^{
                dispatch_semaphore_signal(uploadSemaphore);
            }];
        });
    }
}
```

### 2.10 `pthread_rwlock_t`（读写锁）

POSIX 标准的读写锁，允许多个读者并发，但写者独占。

**特点**：
- **读-读**：可并发
- **读-写**：互斥
- **写-写**：互斥
- 写者优先级高于读者（避免读者饿死）

**使用示例**：
```objc
#import <pthread.h>

@interface RouterManager : NSObject {
    pthread_rwlock_t _rwlock;
    NSDictionary *_routes;
}
@end

@implementation RouterManager

- (instancetype)init {
    self = [super init];
    if (self) {
        pthread_rwlock_init(&_rwlock, NULL);
        _routes = @{};
    }
    return self;
}

// 读操作（可并发）
- (NSString *)routeForPath:(NSString *)path {
    pthread_rwlock_rdlock(&_rwlock);
    NSString *target = _routes[path];
    pthread_rwlock_unlock(&_rwlock);
    return target;
}

// 写操作（独占）
- (void)updateRoutes:(NSDictionary *)newRoutes {
    pthread_rwlock_wrlock(&_rwlock);
    _routes = [newRoutes copy];
    pthread_rwlock_unlock(&_rwlock);
}

- (void)dealloc {
    pthread_rwlock_destroy(&_rwlock);
}

@end
```

**适用场景**：读多写少的数据结构（配置表、路由表、缓存查询）。

### 2.11 `atomic` 属性修饰符

**原理**：底层使用自旋锁（早期）或互斥锁（现代）保证 `setter` / `getter` 的原子性。

**注意**：
- 仅保证单次读写安全，不保证整体线程安全
- 性能开销较大（比 `nonatomic` 慢约 10-20 倍）
- 一般仅用于跨线程的基础类型传递

```objc
@property (atomic, assign) NSInteger count; // 仅保证 count 赋值/读取是原子的
// 但 self.count++ 仍不安全（读-改-写三步非原子）
```

## 三、性能对比

### 3.1 性能排名（由高到低）

基于大量加锁/解锁操作的基准测试（数据仅供参考，实际因硬件/系统版本/负载而异）：

```
OSSpinLock (已废弃) 
    > dispatch_semaphore 
    > os_unfair_lock 
    > pthread_mutex 
    > NSLock 
    > NSCondition 
    > pthread_mutex(recursive) 
    > NSRecursiveLock 
    > NSConditionLock 
    > @synchronized
```

### 3.2 性能梯队

| 梯队       | 锁类型                                | 说明                     |
| :--------- | :------------------------------------ | :----------------------- |
| 🥇 第一梯队 | `OSSpinLock`(已废)、`os_unfair_lock`  | 极轻量，临界区极短时最优 |
| 🥈 第二梯队 | `dispatch_semaphore`、`pthread_mutex` | 性能优秀，功能强大       |
| 🥉 第三梯队 | `NSLock`、`NSCondition`               | OC 封装，易用性好        |
| 第四梯队   | `NSRecursiveLock`、`NSConditionLock`  | 特定场景专用，开销较大   |
| 垫底       | `@synchronized`                       | 使用最方便，性能最差     |

### 3.3 性能影响因素

1. **锁竞争强度**：竞争越激烈，性能差异越明显
2. **临界区长度**：临界区越短，锁本身开销占比越大
3. **硬件平台**：真机 vs 模拟器，不同 CPU 架构表现不同
4. **系统版本**：苹果在不同 iOS 版本中持续优化锁实现

## 四、实战场景与选型指南

### 4.1 场景速查表

| 场景                 | 推荐锁                                  | 理由               |
| :------------------- | :-------------------------------------- | :----------------- |
| 高性能缓存/计数器    | `os_unfair_lock` / `dispatch_semaphore` | 极轻量，性能最优   |
| 控制并发数量（限流） | `dispatch_semaphore`                    | 天然支持资源计数   |
| 常规互斥，无嵌套调用 | `NSLock` / `pthread_mutex`              | 性能与易用性平衡   |
| 递归函数 / 嵌套调用  | `NSRecursiveLock`                       | 防止同线程死锁     |
| 生产者-消费者        | `NSCondition`                           | 支持条件等待/通知  |
| 顺序任务执行         | `NSConditionLock`                       | 依赖整数值条件     |
| 读多写少             | `pthread_rwlock_t`                      | 读者并发，提升性能 |
| 快速原型/调试        | `@synchronized`                         | 使用最简单         |
| 异步转同步（带超时） | `NSCondition` / `dispatch_semaphore`    | 支持超时控制       |
| 防重复网络请求       | `NSCondition`                           | 广播唤醒           |

### 4.2 决策树

```
是否需要控制并发数量？
    ├─ 是 → dispatch_semaphore
    └─ 否 → 是否存在同线程嵌套加锁？
                ├─ 是 → NSRecursiveLock
                └─ 否 → 是否读多写少？
                            ├─ 是 → pthread_rwlock_t
                            └─ 否 → 是否需要线程间通信（等待/通知）？
                                        ├─ 是 → NSCondition / NSConditionLock
                                        └─ 否 → 对性能要求是否极高？
                                                    ├─ 是 → os_unfair_lock
                                                    └─ 否 → NSLock
```

### 4.3 典型场景详解

下面列举 **11 个真实开发中的典型场景**，详细说明为什么选择对应的锁。

---

#### 场景 1：图片/网络请求内存缓存（NSCache 底层保护）
- **场景描述**：App 维护一个全局 `NSMutableDictionary` 作为图片缓存。UI 滑动时，主线程和子线程**高频并发读取**；图片下载完成后，后台线程**偶尔写入**。
- **推荐锁**：**`pthread_rwlock_t`（读写锁）**
- **选型理由**：
  - **读多写少**：滑动列表时读操作占 99%，写操作仅在下载完成时触发。
  - **并发读**：读写锁允许多个读线程同时进入，屏幕滑动时不会因为锁竞争导致卡顿（FPS 提升明显）。
  - **写独占**：写入时锁住所有读写操作，保证数据一致性。
- **❌ 不选 `NSLock` 的原因**：普通互斥锁即使读操作也要排队，高并发读场景下性能损耗较大。

---

#### 场景 2：App 启动埋点计数器（统计点击次数）
- **场景描述**：多个业务线程（网络回调、UI 事件）同时调用 `self.clickCount++`，仅做累加操作。
- **推荐锁**：**`os_unfair_lock`**
- **选型理由**：
  - **临界区极短**：仅仅是一条整形加法指令（纳秒级）。
  - **开销最小**：`os_unfair_lock` 是 iOS 中最轻量级的互斥锁，比信号量更节省资源。
  - **安全替代**：虽然临界区短适合自旋，但 `OSSpinLock` 有优先级反转问题，所以用 `os_unfair_lock`（它会适当自旋+休眠混合策略）是最优解。

---

#### 场景 3：控制同时上传/下载的最大并发数（限流）
- **场景描述**：相册批量上传，需要限制**同时最多 3 个任务**在后台运行，防止蜂窝网络带宽占满或服务器压力过大。
- **推荐锁**：**`dispatch_semaphore`（信号量）**
- **选型理由**：
  - **天然支持资源计数**：信号量初始值设为 3，每个任务开始时 `wait`，结束时 `signal`。
  - **直接对应并发数**：无需额外维护队列状态，代码简洁且性能极高。
  - **阻塞策略明确**：当并发数达到上限时，后续任务线程自动挂起，等待释放。

---

#### 场景 4：文件目录递归遍历计算总大小（递归调用）
- **场景描述**：写一个递归函数 `- (long long)sizeOfFolder:(NSString *)path`，内部遍历子文件夹并累加文件大小，需要保证累加操作线程安全。
- **推荐锁**：**`NSRecursiveLock`**
- **选型理由**：
  - **强递归属性**：函数调用自身，同一个线程会多次进入加锁代码块。
  - **防死锁**：使用 `NSLock` 会在第二次递归调用时死锁（因为锁已被当前线程持有）。递归锁允许重入，只累加计数，彻底解决该问题。

---

#### 场景 5：复杂状态机（音频播放器：暂停/播放/停止）
- **场景描述**：播放器有状态枚举 `isPlaying` / `isPaused` / `isStopped`。UI 按钮和系统音频中断回调可能同时触发状态变更，且 `stop` 方法内部会调用 `pause` 方法（存在嵌套调用风险）。
- **推荐锁**：**`NSRecursiveLock`**
- **选型理由**：
  - **调用链嵌套**：因为存在方法互相调用（`stop` -> `pause`），锁会被同一线程多次获取。
  - **状态保护**：递归锁能安全处理这种复杂的调用链，同时保证 `state` 切换时的线程安全。

---

#### 场景 6：异步任务等待回调（将异步转同步，带超时）
- **场景描述**：在单元测试或特定业务中，需要发一个网络请求，必须**阻塞当前子线程**等待结果返回，并设置 5 秒超时。
- **推荐锁**：**`dispatch_semaphore`**（轻量）或 **`NSCondition`**
- **选型理由**：
  - **超时支持**：`dispatch_semaphore_wait` 可设置超时时间，`NSCondition` 的 `waitUntilDate:` 同样支持。
  - **显式唤醒**：网络回调回来时，通过 `signal` 精准唤醒等待的线程。
  - **性能优先**：`dispatch_semaphore` 更轻量，适合这种简单等待场景。
- **📌 注意**：绝对不要在主线程使用，否则 App 会卡死。示例：
```objc
dispatch_semaphore_t sema = dispatch_semaphore_create(0);
[network requestWithCompletion:^{
    // 处理数据...
    dispatch_semaphore_signal(sema);
}];
dispatch_semaphore_wait(sema, dispatch_time(DISPATCH_TIME_NOW, 5 * NSEC_PER_SEC));
```

---

#### 场景 7：多个任务按严格顺序执行（任务 A -> B -> C）
- **场景描述**：启动时需要依次加载：A(读取配置) -> B(初始化数据库) -> C(进入首页)。必须等上一个完成，下一个才能开始。
- **推荐锁**：**`NSConditionLock`**
- **选型理由**：
  - **条件绑定的锁**：任务 B 设置 `lockWhenCondition:1`，任务 A 完成后 `unlockWithCondition:1`，天然实现顺序依赖。
  - **代码可读性好**：相比手动管理 `dispatch_group` 或信号量，`NSConditionLock` 通过整数值直观表达了执行阶段。

---

#### 场景 8：防重复网络请求（Token 过期刷新 / 数据预加载去重）
- **场景描述**：首页同时发了 10 个请求，发现 Token 过期。如果 10 个请求各自去刷新 Token，会造成严重资源浪费和并发冲突。
- **推荐锁**：**`NSCondition`**（参考刷新 Token 示例）
- **选型理由**：
  - **广播唤醒**：当一个线程去刷新时，其余 9 个线程调用 `wait` 挂起。刷新完成后调用 `broadcast`，一次性唤醒所有等待的线程，复用新 Token 重试。
  - **锁释放机制**：`wait` 会释放锁，使得刷新线程能够正常获取锁去执行网络操作。

---

#### 场景 9：数据模型整体更新（User 对象替换）
- **场景描述**：`UserModel` 包含姓名、年龄、地址等 10 个属性。后台返回新数据时需要整体替换，且 UI 多个模块会并发读取。
- **推荐锁**：**`NSLock`（或 `pthread_mutex`）**
- **选型理由**：
  - **保护完整“事务”**：替换 10 个属性必须原子性完成，中间不能有读取者看到“半成品”对象。普通互斥锁即可胜任。
  - **适中性能**：`NSLock` 封装友好，性能适中，对于这种非高频操作（网络回调）完全够用。
  - **无嵌套风险**：该业务逻辑简单，没有递归调用，不需要递归锁带来的额外开销。

---

#### 场景 10：快速开发/原型验证/调试开关
- **场景描述**：新产品快速迭代，写一个工具类单例，或者临时加个调试开关保护，希望用最少的代码保证线程安全。
- **推荐锁**：**`@synchronized`**
- **选型理由**：
  - **开发效率最高**：一行代码搞定，不用声明锁对象。
  - **递归支持**：不用担心同一个方法被多次调用会死锁。
- **⚠️ 警告**：一旦进入稳定期，如果是高频调用路径（如列表 Cell 复用），必须替换为 `dispatch_once`（单例）或 `NSLock`（互斥），因为 `@synchronized` 的性能开销是普通锁的 5-10 倍。

---

#### 场景 11：严格单例（只创建一次）
- **场景描述**：`sharedInstance` 方法确保对象只创建一次，且调用频率极高（每次获取单例都调用）。
- **推荐锁**：**`dispatch_once`**（GCD 单例）
- **选型理由**：
  - **绝对安全且性能极致**：`dispatch_once` 是编译器优化过的，比 `@synchronized` 快很多。
  - **语义清晰**：它就是为“只执行一次”量身定做的，不用白不用。

---

### 4.4 关键禁忌

1. **绝对避免在主线程使用阻塞锁**（`lock` / `wait`），否则界面卡死，触发 Watchdog 崩溃。
2. **禁止在新代码中使用 `OSSpinLock`**，使用 `os_unfair_lock` 替代。
3. **`@synchronized` 不宜在循环或高频调用的热点路径中使用**。
4. **`atomic` 不保证对象整体线程安全**，只保证单次读写原子性。
5. **递归锁不应滥用**，仅在确实存在嵌套加锁时使用，否则会掩盖设计问题。

## 五、底层实现简析

### 5.1 锁的底层依赖

```
┌─────────────────────────────────────────────────────┐
│                   应用层锁                          │
├─────────────┬─────────────┬───────────────────────┤
│  @synchronized │ NSLock    │ NSCondition           │
│  NSRecursiveLock │ NSConditionLock               │
└─────────────┴─────────────┴───────────────────────┘
                      │
                      ▼
┌─────────────────────────────────────────────────────┐
│              pthread_mutex (POSIX)                  │
│         + pthread_cond (条件变量)                   │
└─────────────────────────────────────────────────────┘
                      │
                      ▼
┌─────────────────────────────────────────────────────┐
│               Mach / BSD 内核                       │
│         (系统级同步原语)                            │
└─────────────────────────────────────────────────────┘
```

### 5.2 关键底层实现

| 锁                | 底层实现                                        |
| :---------------- | :---------------------------------------------- |
| `os_unfair_lock`  | 内核级互斥锁，基于 Mach 同步原语                |
| `pthread_mutex`   | POSIX 线程库，调用系统级 `__psynch_mutexwait`   |
| `NSLock`          | 封装 `pthread_mutex`                            |
| `NSRecursiveLock` | 封装 `pthread_mutex` + 递归属性                 |
| `NSCondition`     | 封装 `pthread_mutex` + `pthread_cond`           |
| `@synchronized`   | 编译后调用 `objc_sync_enter/exit`，底层是递归锁 |

### 5.3 递归锁的计数机制

```objc
// 递归锁内部结构（简化）
typedef struct {
    thread_t owner;   // 持有锁的线程
    int count;        // 加锁次数
    pthread_mutex_t mutex; // 底层互斥锁
} recursive_lock_t;

// 加锁流程
void recursive_lock_lock(recursive_lock_t *lock) {
    if (lock->owner == current_thread) {
        lock->count++;  // 同线程 → 仅计数
    } else {
        pthread_mutex_lock(&lock->mutex); // 不同线程 → 阻塞
        lock->owner = current_thread;
        lock->count = 1;
    }
}

// 解锁流程
void recursive_lock_unlock(recursive_lock_t *lock) {
    if (--lock->count == 0) {
        lock->owner = NULL;
        pthread_mutex_unlock(&lock->mutex); // 真正释放
    }
}
```

## 六、NSCondition 刷新 Token 实战

结合 `NSCondition` 实现**带超时控制的 Token 刷新机制**，解决并发请求中 Token 过期的问题。

### 设计思路

1. 多个并发请求发现 Token 过期，**只允许一个线程**执行刷新操作
2. 其余线程等待刷新完成或超时
3. 支持可配置的超时时间（如 30 秒）

### 完整实现

```objc
// TokenManager.h
@interface TokenManager : NSObject
+ (instancetype)sharedManager;
- (BOOL)refreshTokenWithTimeout:(NSTimeInterval)timeout;
@end

// TokenManager.m
@interface TokenManager () {
    NSCondition *_condition;
    BOOL _isRefreshing;
    BOOL _refreshSuccess;
}
@end

@implementation TokenManager

+ (instancetype)sharedManager {
    static TokenManager *instance = nil;
    static dispatch_once_t onceToken;
    dispatch_once(&onceToken, ^{
        instance = [[self alloc] init];
    });
    return instance;
}

- (instancetype)init {
    self = [super init];
    if (self) {
        _condition = [[NSCondition alloc] init];
        _isRefreshing = NO;
        _refreshSuccess = NO;
    }
    return self;
}

- (BOOL)refreshTokenWithTimeout:(NSTimeInterval)timeout {
    [_condition lock];

    if (_isRefreshing) {
        // 已有线程在刷新 → 当前线程等待
        NSDate *timeoutDate = [NSDate dateWithTimeIntervalSinceNow:timeout];
        while (_isRefreshing) {
            if (![_condition waitUntilDate:timeoutDate]) {
                // 超时
                [_condition unlock];
                return NO;
            }
        }
        BOOL result = _refreshSuccess;
        [_condition unlock];
        return result;
    } else {
        // 当前线程负责刷新
        _isRefreshing = YES;
        _refreshSuccess = NO;
        [_condition unlock];

        // 执行刷新（模拟网络请求）
        BOOL success = [self performRefresh];

        // 刷新完成 → 广播唤醒所有等待线程
        [_condition lock];
        _isRefreshing = NO;
        _refreshSuccess = success;
        [_condition broadcast];
        [_condition unlock];

        return success;
    }
}

- (BOOL)performRefresh {
    // 模拟同步网络请求，耗时 1~3 秒
    [NSThread sleepForTimeInterval:2.0];
    return arc4random_uniform(10) < 9; // 90% 成功率
}

@end
```

### 使用方式

```objc
// 在子线程中调用
dispatch_async(dispatch_get_global_queue(0, 0), ^{
    BOOL success = [[TokenManager sharedManager] refreshTokenWithTimeout:30.0];
    if (success) {
        NSLog(@"Token 刷新成功");
    } else {
        NSLog(@"刷新失败或超时，跳转登录");
    }
});
```

### 注意事项

- **必须在子线程调用**，避免阻塞主线程导致 UI 卡顿
- 大量线程同时等待时，内存和线程池资源需关注
- 推荐使用**异步回调**方式替代同步阻塞

## 七、总结

### 7.1 核心要点

1. **锁的本质**：用空间（内存/CPU）换时间（数据安全），或反之。
2. **选择原则**：在性能、安全性和开发便利性之间做权衡。
3. **递归锁**：解决同线程嵌套加锁问题，但不应滥用。
4. **条件锁**：适合需要线程间通信的场景。
5. **信号量**：功能强大，可同时实现互斥和并发控制。

### 7.2 一句话速记表

| 锁                   | 一句话总结                         |
| :------------------- | :--------------------------------- |
| `os_unfair_lock`     | 极轻量，替代废弃自旋锁             |
| `dispatch_semaphore` | 万能工具，互斥 + 限流 + 异步转同步 |
| `NSLock`             | 日常首选，平衡之选                 |
| `NSRecursiveLock`    | 防嵌套死锁，递归专用               |
| `NSCondition`        | 锁 + 通知，线程通信，支持广播      |
| `NSConditionLock`    | 基于整数值的顺序控制               |
| `pthread_rwlock_t`   | 读多写少，并发读取                 |
| `@synchronized`      | 最方便，性能最差                   |
| `atomic`             | 仅保证单次读写原子性               |
| `dispatch_once`      | 单例专用，极致性能                 |

### 7.3 选型黄金法则

如果你的场景介于两者之间，优先选择 **`NSLock`** 或 **`dispatch_semaphore`**。它们覆盖了 80% 的业务场景，且性能优秀，属于“万金油”方案。只有在明确遇到性能瓶颈或递归风险时，再考虑极端优化方案。
