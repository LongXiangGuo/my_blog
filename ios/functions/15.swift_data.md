# SwiftData 完全指南：从入门到深度实战

> 基于 WWDC 2023 发布的 SwiftData 框架，系统梳理核心概念、架构原理、数据迁移、并发管理及性能优化等关键知识点。

---

## 一、SwiftData 是什么

SwiftData 是 Apple 于 WWDC 2023 推出的**现代数据持久化框架**，支持 iOS 17+、macOS 14+、watchOS 10+ 等全 Apple 平台。它的核心特点包括：

- **纯 Swift 代码建模**：无需 XML 模型文件或可视化编辑器，直接通过 `@Model` 宏将 Swift 类标记为可持久化模型
- **与 SwiftUI 深度集成**：提供 `@Query` 宏自动获取数据并驱动视图更新
- **基于 Core Data 存储引擎**：复用 Core Data 经过多年验证的稳定持久化技术
- **非侵入式设计**：补充而非替代你现有的模型类

> **核心认知**：SwiftData **不是** Core Data 的简单封装，而是与 Core Data **共享同一持久化引擎**但完全独立的堆栈。

---

## 二、核心架构：三大组件

SwiftData 的架构围绕三个核心组件构建：

| 组件               | 角色                           | 类比               |
| ------------------ | ------------------------------ | ------------------ |
| **ModelContainer** | 数据中枢，连接模型与持久化存储 | 图书馆本身         |
| **Schema**         | 数据结构说明书，描述模型定义   | 图书馆的藏书规则   |
| **ModelContext**   | 操作数据的"工作台"，执行 CRUD  | 图书馆的前台工作台 |

### 1. ModelContainer（数据容器）

负责管理数据模型、创建持久化存储（默认 SQLite 文件），并提供 `ModelContext` 供开发者操作数据。

```swift
// 基础创建
let container = try ModelContainer(for: Person.self)

// 自定义配置（内存存储，适合测试）
let config = ModelConfiguration(isStoredInMemoryOnly: true)
let container = try ModelContainer(for: Person.self, configurations: config)
```

### 2. Schema（数据模式）

由 `@Model` 宏自动生成，记录实体的属性类型和关系。可通过 `container.modelSchema` 访问查看。

### 3. ModelContext（数据上下文）

开发者执行**增删改查**的直接接口，所有操作在此进行，最终同步到磁盘。

## 三、@Model 宏的实现原理

当用 `@Model` 修饰一个类时，SwiftData 会：

1. **自动生成 Schema**：分析类的所有存储属性，将其转换为持久化属性
2. **原生适配值类型**：基础类型（String、Int、Float 等）、Struct、Enum、Codable 类型均可直接作为属性
3. **引用类型自动转为关系**：模型之间的引用自动成为 Relationship
4. **支持元数据定制**：通过 `@Attribute`（唯一性约束）、`@Relationship`（删除规则）、`@Transient`（排除属性）等宏精细控制

### 与 Core Data 的关系

SwiftData 复用了 Core Data 的持久化引擎，但提供了**更现代、更 Swift 风格**的 API。两者可以在同一 App 中共存，指向相同的底层存储。

## 四、完整工作流

```
1. 定义模型
   └── 用 @Model 修饰 Swift 类

2. 创建 ModelContainer
   └── 指定 Schema 和 ModelConfiguration

3. 注入到 SwiftUI 环境
   └── 使用 .modelContainer() 修饰符

4. 查询数据
   └── 使用 @Query 宏或自定义 FetchDescriptor

5. 操作数据
   └── 通过 ModelContext 执行 insert/delete/save

6. 视图自动更新
   └── SwiftData 自动通知 SwiftUI 数据变更
```

### 代码示例：统一创建容器

```swift
static func appModelContainer(
    inMemoryOnly: Bool = false, isStub: Bool = false
) throws -> ModelContainer {
    let schema = Schema.appSchema
    let modelConfiguration = ModelConfiguration(
        isStub ? "stub" : nil, 
        schema: schema, 
        isStoredInMemoryOnly: inMemoryOnly
    )
    return try ModelContainer(for: schema, configurations: [modelConfiguration])
}
```

**设计亮点**：
- 通过 `inMemoryOnly` 参数灵活切换**生产环境**（持久化）和**测试环境**（内存存储）
- 通过 `isStub` 参数支持**预览数据**（stub）与**正式数据**隔离

## 五、数据查询与修改流程

### 查询流程：从 UI 到 SQL

查询的入口通常是 SwiftUI 的 `@Query` 宏，或手动创建的 `FetchDescriptor`。

1. **宏展开（编译时）**：`#Predicate` 宏将 Swift 闭包捕获为语法树，转化为 `Foundation.Predicate`；`@Query` 宏生成 `@StateObject` 并监听数据变化
2. **执行 Fetch（运行时）**：`@Query` 通过环境获取 `ModelContext`，将谓词翻译为 Core Data 的 `NSPredicate`，最终编译成 SQLite 的 SELECT 语句
3. **Fault（故障）机制**：执行 SQL 后只加载对象的 ID 和元数据，创建 Fault 对象占位，访问具体属性时才触发第二次查询

### 修改流程：从属性赋值到磁盘

1. **变更追踪**：`@Model` 宏为类注入 `ManagedObjectObserver`，每个 `ModelContext` 维护 `registeredObjects` 注册表和 `changedObjects` 脏对象列表。赋值时只将对象标记为"脏"，不立即写磁盘
2. **保存事务打包**：调用 `save()` 时，验证约束、检测冲突（乐观锁），将变更生成 SQL 语句（UPDATE/INSERT/DELETE），在 `BEGIN TRANSACTION` 和 `COMMIT` 之间提交
3. **逆向关系自动维护**：修改 `@Relationship` 一方时，`save()` 时自动检查并更新对方反向指针

```swift
// 查询流程
let descriptor = FetchDescriptor<User>(
    predicate: #Predicate { $0.isActive == true },
    sortBy: [SortDescriptor(\.name)]
)
let activeUsers = try context.fetch(descriptor)

// 修改流程
activeUsers.first?.name = "Tim"  // 标记为 Dirty
let newUser = User(name: "Cook")
context.insert(newUser)          // 标记为 Insert
context.delete(activeUsers.first!) // 标记为 Delete
try context.save()               // 统一提交为原子事务
```

## 六、数据模型升级与迁移

### 版本化 Schema

当模型发生变更（增删属性、修改关系等），需要进行数据迁移。

### 核心机制

1. **VersionedSchema**：为每个版本定义独立的 Schema 枚举，实现 `VersionedSchema` 协议
2. **SchemaMigrationPlan**：描述各版本之间的迁移规则

### 实现步骤

#### 步骤一：定义每个版本的 Schema

```swift
// 版本 1
enum UsersSchemaV1: VersionedSchema {
    static var versionIdentifier = Schema.Version(1, 0, 0)
    static var models: [any PersistentModel.Type] { [User.self] }
    
    @Model final class User {
        var name: String
        var age: Int
    }
}

// 版本 2：对 name 添加 .unique 约束
enum UsersSchemaV2: VersionedSchema {
    static var versionIdentifier = Schema.Version(2, 0, 0)
    static var models: [any PersistentModel.Type] { [User.self] }
    
    @Model final class User {
        @Attribute(.unique) var name: String
        var age: Int
    }
}

typealias User = UsersSchemaV2.User
```

#### 步骤二：创建迁移计划

```swift
enum UsersMigrationPlan: SchemaMigrationPlan {
    static var schemas: [any VersionedSchema.Type] {
        [UsersSchemaV1.self, UsersSchemaV2.self]
    }

    static let migrateV1toV2 = MigrationStage(
        from: UsersSchemaV1.self, to: UsersSchemaV2.self
    ) { context in
        // 自定义迁移逻辑：处理去重等
        let oldUsers = try context.fetch(FetchDescriptor<UsersSchemaV1.User>())
        for oldUser in oldUsers {
            let newUser = UsersSchemaV2.User(
                name: oldUser.name,
                age: oldUser.age
            )
            context.insert(newUser)
        }
        try context.save()
    } didMigrate: { context in
        print("Migration from V1 to V2 completed.")
    }

    static var stages: [MigrationStage] {
        [migrateV1toV2]
    }
}
```

#### 步骤三：应用迁移计划

```swift
let container = try ModelContainer(
    for: UsersSchemaV2.self,
    migrationPlan: UsersMigrationPlan.self
)
```

### 迁移类型速查

| 迁移类型                                  | 是否需要自定义代码 |
| :---------------------------------------- | :----------------- |
| 添加带默认值的属性                        | ❌ 自动             |
| 重命名属性（`@Attribute(originalName:)`） | ❌ 自动             |
| 删除属性                                  | ❌ 自动             |
| 添加 `.unique` 约束（需去重）             | ✅ 必须             |
| 属性类型改变                              | ✅ 必须             |
| 拆分/合并属性                             | ✅ 必须             |
| 复杂关系变更                              | ✅ 必须             |

> **重要**：从一个未版本化的 Schema 迁移到版本化 Schema 是**可行**的，但需要将所有模型放入 `VersionedSchema` 中。

## 七、线程访问与并发原理

### 核心结论

- **`ModelContext` 是非线程安全的**，绑定到创建它的线程/Actor
- **`@Model` 对象实例不能跨线程传递**，只能传递 `persistentModelID`
- **`ModelContainer` 是线程安全的**，可以共享

### 深层原理

1. **私有变更追踪**：每个 Context 维护着"注册对象图"和"变更集合"，**没有加锁**，依赖单线程执行保证性能。多线程同时操作同一 Context 会导致数据竞争（Data Race）

2. **惰性加载与行缓存**：对象在 Context 中缓存行，跨线程访问会抛出 `EXC_BAD_ACCESS`

3. **保存时的乐观锁**：多线程同时操作同一份数据，SQLite 报错 `SQLITE_BUSY`

### 线程安全解决方案

#### 方法一：传递 `persistentModelID`

```swift
// 1. 主线程拿到 ID（线程安全）
let userID = user.persistentModelID

// 2. 后台线程
Task.detached {
    let backgroundContext = ModelContext(modelContainer)
    if let backgroundUser = backgroundContext.model(for: userID) as? User {
        backgroundUser.name = "New Name"
        try backgroundContext.save()
    }
}
```

#### 方法二：使用 `ModelActor`（推荐，Swift 6 并发）

```swift
@ModelActor
actor DataHandler {
    func updateUser(id: PersistentIdentifier, newName: String) throws {
        guard let user = self.model(for: id) as? User else { return }
        user.name = newName
        try self.modelContext.save()
    }
}

// 调用
Task {
    let handler = DataHandler(modelContainer: container)
    await try handler.updateUser(id: userID, newName: "Swift")
}
```

### 避坑指南

| ❌ 错误写法                               | ✅ 正确写法                                  |
| :--------------------------------------- | :------------------------------------------ |
| 后台 Task 中直接引用主线程的 `self.user` | 传递 `persistentModelID`，在后台重新 Fetch  |
| 后台线程共用主线程的 `ModelContext`      | 后台使用 `ModelContext(container)` 新建实例 |
| 用 `DispatchQueue.global()` 操作 Context | 使用 `ModelActor` 或 `Task` + `await`       |

## 八、ModelContainer、ModelContext 与对象的对应关系

### 核心对应关系速览

| 关系维度                          | 对应关系            | 关键规则                                         |
| :-------------------------------- | :------------------ | :----------------------------------------------- |
| **ModelContainer → ModelContext** | **1 : N（一对多）** | 一个容器可以创建无数个独立的 Context             |
| **ModelContext → Model（对象）**  | **1 : N（一对多）** | 一个 Context 可以持有并管理无数个对象            |
| **Model（对象） → ModelContext**  | **N : 1（多对一）** | **一个对象实例只能归属于创建它的那一个 Context** |

### 为什么 Container 可以创建无数个 Context？

- **重型资源被 Container 独占**：Schema、数据库连接等由 Container 持有且线程安全
- **Context 只持有"软引用"**：创建 Context 只是新建一个空的变更追踪字典，成本极低
- **事务隔离需求**：每个并发操作（UI 主线程、后台导入、临时草稿）独立 Context，避免加锁开销

### 为什么 Context 可以持有无数个对象？

- **唯一性保证**：同一 `persistentModelID` 在同一个 Context 内永远只对应一个对象实例，Context 维护缓存哈希表
- **Fault 机制**：绝大多数对象在创建初期只是"空壳"，只有访问属性时才触发数据库查询
- **批量操作**：`save()` 时将变更打包生成 SQL 字符串，以批处理方式提交

### ModelContainer 是单例吗？

**技术上不是**，但**工程上必须当作单例使用**：

- 对同一个 SQLite 文件创建多个 Container 会导致协调器冲突，引发 `SQLITE_BUSY` 或闪退
- SwiftUI 的 `.modelContainer()` 修饰符内部复用已有实例
- 合法多容器场景：完全隔离的数据库文件 或 内存存储（测试/预览）

```swift
@main
struct MyApp: App {
    let container: ModelContainer = {
        let config = ModelConfiguration(url: ...)
        return try! ModelContainer(for: User.self, configurations: config)
    }()

    var body: some Scene {
        WindowGroup {
            ContentView()
                .modelContainer(container) // 注入唯一实例
        }
    }
}
```

## 九、Faulting 机制与大数据量优化

### Faulting 机制是什么？（"纸老虎"原理）

**一句话定义**：Faulting（故障机制）是 SwiftData/Core Data 为了节省内存而设计的**"占位符"**机制。查询时，SwiftData 只返回一个"空壳对象"（Fault），这个空壳只记录了该对象的唯一 ID（`persistentModelID`），但它的所有属性值（如 `name`、`age`）在此时**完全不存在于内存中**。

### Fault 的触发时机

Fault 在以下情况下会被**触发（Fire）**，去数据库拉取真实数据：

1. **显式访问非 ID 属性**：执行 `print(user.name)` 时，SwiftData 立即拦截，去 SQLite 执行 `SELECT ... WHERE id = ?` 并填充属性
2. **访问未被预取的关系**：执行 `print(user.orders.count)`，且 `orders` 没有被预加载时，触发 Fault 去查询关联表
3. **调用 `refresh(_: mergeChanges:)`**：`context.refresh(someObject, mergeChanges: false)` 会强制将对象变回 Fault 状态，释放内存

> **重要**：`persistentModelID` 是**唯一不会触发 Fault** 的属性，因为它存储在对象元数据中，不依赖数据库查询。这也是为什么跨线程传递 ID 极其高效且安全。

### 大数据量优化阈值

| 数据量级          | 主线程 `@Query` 体验       | 建议策略                                     |
| :---------------- | :------------------------- | :------------------------------------------- |
| **< 500 条**      | 丝滑流畅，毫无感知         | 直接使用 `@Query` 即可                       |
| **500 ~ 2000 条** | 轻微卡顿，滑动列表可能掉帧 | **必须启用** `fetchLimit` 分页               |
| **2000 ~ 1万条**  | 内存飙升，UI 明显冻结      | **必须后台异步** + **分页** + **预加载关系** |
| **> 1万条**       | 极易 OOM（内存溢出）       | **禁止** 一次性加载，必须分批且后台执行      |

> **结论**：查询结果预期**超过 1000 条**，就不应把结果集全部暴露给 `@Query`，必须进行分页（Pagination）并将数据获取/处理放到后台 `Actor` 中。

### 后台异步操作 + 分页实战

#### 1. 定义后台数据处理器（基于 `ModelActor`）

```swift
@ModelActor
actor BackgroundDataHandler {
    
    // 后台分页查询（返回 ID 数组，不触发 Fault）
    func fetchPage(page: Int, pageSize: Int) throws -> [PersistentIdentifier] {
        let descriptor = FetchDescriptor<User>(
            sortBy: [SortDescriptor(\.createdAt)]
        )
        descriptor.fetchLimit = pageSize
        descriptor.fetchOffset = page * pageSize
        
        let users = try context.fetch(descriptor)
        
        // ⚠️ 不返回 User 对象本身（不能跨 Actor）
        // 只返回 ID，主线程用 ID 重新获取
        return users.map { $0.persistentModelID }
    }

    // 后台大数据插入（分批提交，防止内存峰值）
    func batchInsert(count: Int) async throws {
        let batchSize = 1000
        
        for i in 0..<(count / batchSize) {
            for j in 0..<batchSize {
                let user = User(name: "User_\(i * batchSize + j)")
                context.insert(user)
            }
            try context.save()      // 每批保存一次
            context.reset()          // 重置缓存，防止内存无限增长
        }
    }
}
```

#### 2. 在 SwiftUI 中调用

```swift
struct UserListView: View {
    @Environment(\.modelContext) private var mainContext
    @State private var currentPage = 0
    @State private var userIDs: [PersistentIdentifier] = []
    let pageSize = 20 // UI 层面每页只加载 20 条
    
    var body: some View {
        List(userIDs, id: \.self) { id in
            if let user = mainContext.model(for: id) as? User {
                Text(user.name)
            }
        }
        .task {
            await loadNextPage()
        }
    }
    
    func loadNextPage() async {
        let handler = BackgroundDataHandler(modelContainer: mainContext.container)
        let ids = try? await handler.fetchPage(page: currentPage, pageSize: pageSize)
        if let ids = ids, !ids.isEmpty {
            await MainActor.run {
                self.userIDs.append(contentsOf: ids)
                self.currentPage += 1
            }
        }
    }
}
```

### 后台异步避坑指南

| ❌ 误区                           | ✅ 正确做法                                                       |
| :------------------------------- | :--------------------------------------------------------------- |
| 后台查询完把 `[User]` 传回主线程 | 传回 `[PersistentIdentifier]`，主线程用 `model(for:)` 获取       |
| 后台修改数据后，主线程不刷新     | SwiftData 自动合并通知，`@Query` 会自动刷新                      |
| 分页只设置 `fetchLimit`          | 海量数据时结合 `#Predicate` 按时间戳过滤，避免 `OFFSET` 性能问题 |

## 十、SwiftData、Core Data 与 SQLite 对比

| 特性维度           | SwiftData                             | Core Data                          | SQLite                              |
| :----------------- | :------------------------------------ | :--------------------------------- | :---------------------------------- |
| **本质**           | 基于 Core Data 的高层封装             | 成熟的对象图与持久化框架           | 轻量级嵌入式关系型数据库            |
| **API 与易用性**   | **现代、声明式**，与 SwiftUI 深度集成 | **复杂、历史悠久**，大量样板代码   | **底层、直接**，需编写 SQL 语句     |
| **并发与线程安全** | 基于 **Actor**，**编译器**检查        | 基于 **队列** 和 `perform`，靠自觉 | WAL 日志模式 + 读写锁               |
| **内存管理**       | **Faulting** 机制，内存占用略高       | 成熟的 Faulting 和缓存机制         | 开发者自行控制，极致内存效率        |
| **读写效率**       | 批量操作可能不如 Core Data            | 多年优化，大量数据时更优           | **原生性能最高**，可优化 SQL 和索引 |
| **数据迁移**       | `VersionedSchema` + `MigrationStage`  | 成熟强大的迁移工具                 | 手动编写迁移脚本                    |
| **适用场景**       | **新项目、SwiftUI 应用**              | **复杂模型、遗留项目**             | **极致性能、跨平台**                |

### 选择建议

- **新项目 + 纯 SwiftUI**：**SwiftData** 是首选
- **复杂数据模型 + 极致稳定性**：**Core Data** 依然可靠
- **最高性能 + 底层控制 + 跨平台**：直接使用 **SQLite**

## 总结速查表

| 维度            | 核心要点                                                                  |
| --------------- | ------------------------------------------------------------------------- |
| **定位**        | Swift 原生持久化框架，基于 Core Data 引擎                                 |
| **三大组件**    | ModelContainer（容器）+ Schema（模式）+ ModelContext（上下文）            |
| **@Model 原理** | 宏自动生成 Schema，属性转为持久化属性，引用转为关系                       |
| **工作流**      | 定义模型 → 创建容器 → 注入环境 → 查询/操作 → 自动更新 UI                  |
| **查询流程**    | `#Predicate` → `NSPredicate` → SQL SELECT → Fault 占位                    |
| **修改流程**    | 标记 Dirty → `save()` 打包 → SQL 事务提交 → 通知 UI 刷新                  |
| **迁移**        | VersionedSchema + SchemaMigrationPlan（轻量自动，重量需自定义）           |
| **线程安全**    | Context 绑定线程，对象不可跨线程，使用 `persistentModelID` + `ModelActor` |
| **对象关系**    | Container:Context = 1:N，Context:Object = 1:N，Object:Context = N:1       |
| **Container**   | 技术上非单例，工程上必须单例（同一文件多实例冲突）                        |
| **Faulting**    | 惰性加载占位符，访问属性时触发，`persistentModelID` 不触发                |
| **大数据阈值**  | > 1000 条需分页，> 10000 条必须后台 + 分批                                |
| **性能优化**    | 精准查询、分页加载、预加载关系、批量插入、后台 Actor 执行                 |
| **调试**        | `-com.apple.CoreData.SQLDebug 3` 查看 SQL 日志                            |

> **最后提醒**：SwiftData 虽新，但其成熟度足以支撑生产环境 App。理解其底层原理（尤其是线程模型和 Fault 机制）是避免踩坑的关键。建议在开发中善用 `persistentModelID` 实现跨上下文数据传递，并用 `ModelActor` 规范并发操作。
